# D512 重排模型 A1 閘門報告

## 結論

- **句級（nbest）重排通過全部三項門檻**：在 held-out 7,190 句上，用 dev 選出的操作點 w=0.5、τ=0.5，整句 top-1 由 82.43% 升到 86.59%，+4.16 pp，95% CI [+3.57, +4.76]；有害覆蓋 112 對有益 411（比值 0.27，門檻 1/3）；每句延遲中位 20.2 ms、p95 33.4 ms（門檻 40／100 ms）。
- **詞級（span）重排未達門檻**：23,608 個 span 請求上最佳點只有 +0.80 pp，manifest 操作點 +0.32 pp。原因是 Homa 在多音節 span 上 baseline 已達 95.8%，單音節 span 的增益 CI 跨 0。
- 增益隨句長放大：2–4 音節 +3.4 pp，9–16 音節 +5.7 pp，17–32 音節 +9.6 pp。聊天句庫（最接近日常打字）+4.3 pp，維基百科 +4.1 pp。
- 建議 A2 做**句級**重排、不做詞級，操作點以 w=0.5、τ=0.5 起步，進 IME 後以真實打字重新校準。詳見「建議」。

## 這次量的是什麼

| 項目 | 內容 |
|---|---|
| 引擎 baseline | 唯音 fork `feature/d512-eval` @ 61eb082b 的 Homa 組句器，原廠 CHT 詞庫（VanguardLexicon 4.8.8，TextMap SHA-256 前綴 b7d11e96），**純 unigram、無 POM、無個人選字學習、無 CNS／巨集／半形** |
| 候選來源 | `D512Dump` 以逐音節 insertKey 模擬輸入；nbest 為 k=8 的 beam 路徑（候選 0 必為 Homa 最佳路徑）；span 為最佳路徑上每個節點的同長度 gram |
| 重排模型 | Hugging Face `Funmula/0c-sequence-d512` 固定版 d512-pf512-20260926（MIT），model.onnx SHA-256 71af1f0e…、vocab.json 556dffaf…，與 manifest 一致 |
| 融合規則 | fused = engine_log10 + w × model_logp；非預設候選的 fused 比預設高出 > τ 才覆蓋；單音節 span 走 text 模式 |
| 測試集 | zh-TW 維基百科 64 篇（CC BY-SA 4.0）+ MozTW g0v 聊天句庫（CC0）；文字→注音以正規化 unigram DP 分詞、多音字單字 fallback 整句丟棄（了／的／嗎／呢／吧 例外）、同頻異讀詞條丟棄、gold 全域去重、依文件分割；dev 1,794／held-out 7,190；reviewer 抽 20 筆讀音 0 錯 |
| 操作點選擇 | 只在 dev 上選（見下方「dev 擴充網格」）：dev 最佳 Δ 且有害／有益 ≤ 1/3 的點有三個並列（+3.68 pp），取 w 最小的 (0.5, 0.5)；held-out 的這個點只算一次 |
| 統計 | paired bootstrap 1,000 次重抽的 95% CI；延遲為 onnxruntime 1.31 CPU、intra_op 2 執行緒、逐候選評分、排除暖機；延遲取入庫的 `report-*.md`（第二次執行），與首次執行差 ≤ 0.3 ms |

## 與靈犀論文的對照

論文（CC BY 4.0）第 9 頁：32.6M 模型在 6,000 案例前瞻測試 86.03%，其統計引擎 76.87%，新酷音 64.20%，小麥 67.17%，每例最多 8 候選；論文操作點 (5, 0.25)／(5, 0.5) 是針對他們引擎的分數尺度。本次 Homa 的 log10 unigram 尺度下最佳 w 落在 0.5–1，與模型卡「換引擎須重新校準」一致。本次 baseline 82.4% 高於論文的 76.9%，一部分來自測試集偏向可確定標音的句子，不可直接比較絕對值。

## 注意事項與未驗證項目

1. **baseline 比你日常的引擎弱**：沒有 POM 與個人選字學習，也沒有 CNS、巨集、半形資料。進 IME 後的實際增益沒有量測；推測會小於這裡的 +4 pp（標註：推測），有害覆蓋也可能因個人化而改變。
2. **測試集偏差**：64 篇維基條目與一份打散的聊天句庫，不是你的打字分佈；讀音由詞庫反查、保守丟棄，留下的句子偏向標音可確定者；0c 訓練語料為新聞與財經討論，維基與聊天對模型而言偏域外，增益可能偏保守也可能偏樂觀，無法判定。
3. **候選集**：nbest 的替代路徑來自 standalone 的 unigram beam，不是 IME 內建功能；A2 需在 Homa 加 k-best。候選 0 與正式供給路徑的等價性已用 200 筆真實案例（2,320 個前綴、35,202 個候選）驗證為 0 差異。
4. **延遲**：Python + onnxruntime 逐候選評分的數字；Swift 整合與前綴樹批次評分會不同，且每鍵 20 ms 在整句模式下應只在送出前或停頓時觸發，不宜每鍵重排。
5. **審查**：harness、dumper、測試集各經二到三輪獨立唯讀審查；報告數字由 `reports/gate/report-*.json` 的逐請求模型分數離線重算，與 harness 報告一致。
6. 未做：真人打字實測、prefix-tree 批次評分、neutral_expand_penalty 的宿主端候選擴充、補標點模型。

## 建議

1. **A2 做，但只做句級**：在整句組字結果送出前（或輸入停頓時）對 Homa 的 k-best 路徑重排，不做逐詞 span 重排。
2. 起步操作點 w=0.5、τ=0.5（Homa log10 尺度），做成可開關的實驗功能；進 IME 後用你自己的打字紀錄重新校準，目標是把有害覆蓋壓在有益的 1/3 以下。
3. A2 的工程前置：Homa 增量 k-best（可沿用 D512Dump 的 beam 思路但要走正式 assembler）、Swift 端 onnxruntime 或 CoreML 載入 125 MB 模型、分數融合與門檻設定介面。
